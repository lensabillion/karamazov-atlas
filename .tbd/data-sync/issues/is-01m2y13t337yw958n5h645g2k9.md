The API is a uv project in name only. Make uv the single toolchain, on the
latest stable Python.

PYTHON VERSION — 3.14. As of 20 Sep 2026 the latest stable CPython is 3.14.7;
3.15 exists only as 3.15.0rc1 and FastAPI/pydantic publish no wheels for it, so
it is not a floor to build on. The local venv is ALREADY 3.14.4 and the 12 tests
pass on it, while pyproject says >=3.12 and CI runs 3.12 — so today the tested
interpreter and the shipped interpreter are different, untracked, by accident.

1. Raise `requires-python` to ">=3.14" and add `api/.python-version` = 3.14.
   Update CI's setup to 3.14 and the Dockerfile base to `python:3.14-slim`.
   One version, stated in four places that now agree.
2. `uv lock` and COMMIT `api/uv.lock`. Without it every install resolves fresh:
   CI, Docker and the developer can each get a different FastAPI, and the build
   that passed is not the build that shipped.
3. Move `[project.optional-dependencies] dev` to `[dependency-groups] dev`
   (PEP 735). Dev tooling is not an extra a consumer can install; uv installs
   groups by default and keeps them out of the published wheel.
4. CI: replace `pip install -e ".[dev]"` with `astral-sh/setup-uv@v5` plus
   `uv sync --locked`. `--locked` FAILS if pyproject.toml and uv.lock disagree,
   which is the check that makes committing the lock worth anything.
5. Dockerfile: replace the literal `pip install "fastapi>=0.115" ...` with
   `uv sync --locked --no-dev` from the copied lockfile. That deletes a
   duplicated dependency list that nothing kept in step with pyproject.toml.
   Keep the layer ordering (deps before source) and the existing build-time
   ingest and 96-chapter assertion.
6. `.gitignore` / `.dockerignore`: uv.lock must NOT be ignored; the uv cache
   must be.

Verify: `uv sync --locked` from clean; `uv run python -V` reports 3.14;
`uv run pytest -q` still 12 passed; `docker build` reaches the 96-chapter
assertion; CI python job green.
