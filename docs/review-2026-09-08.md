# Review — 8 September 2026

Reviewed: the whole codebase after design-system v2. Findings are ordered by severity
and each carries a bead. Nothing here is speculative — every item was confirmed by
reading the code or running it.

---

## A. Confirmed bugs

### A1 · Name orbit labels collide once a character has six forms — `atlas-orb1`

`NameOrbit.tsx` places forms around the circle with a fixed angular step:

```ts
const angle = (-140 + i * 61) * (Math.PI / 180);
```

Six forms is `6 × 61° = 366°`, so the sixth form wraps onto the first and the two labels
overlap. No character currently has six forms — Dmitri has four — so it does not fire
today. It will the moment the alias table grows, and it will fail silently.

**Fix:** distribute by `360 / forms.length` with a fixed offset, or place by register
and resolve collisions within a ring.

**Severity:** low now, certain later.

### A2 · Memoised loaders serve stale data after a rebuild — `atlas-memo`

`src/lib/corpus.ts` and `names.ts` cache with `??=`:

```ts
return (_names ??= JSON.parse(readFileSync(...)));
```

The dev server holds the first parse for the life of the process. Re-running a build
script changes the JSON on disk and the running app keeps serving the old data. **This
bit twice during development** — once producing a screenshot that showed corrected data
as still wrong, which nearly sent me chasing a fix that was already in place.

**Fix:** skip the cache when `NODE_ENV !== 'production'`, or key it on file mtime.

**Severity:** medium. It does not affect production, but it makes verification lie.

### A3 · Search reads all 96 chapter files on every query — `atlas-srch`

`searchCorpus()` loops the full chapter list and calls `getChapterText()` for each, so
one query is 96 synchronous file reads plus 96 lowercase copies of the whole novel.

It is survivable at this size and it will not survive spoiler-scoped retrieval, phrase
search, or any concurrent use. It is also the single strongest argument for the database
work in §D.

**Severity:** medium, structural.

## B. Fragility — not broken, but unguarded

### B1 · Curated data has no validation — `atlas-vald`

`relationships.ts` and `timeline.ts` are hand-written. A tie pointing at a person id
that does not exist, or a timeline moment naming someone with no lane, would render as
a silently missing line rather than an error. I checked both by hand during this review
and they are currently clean — which is exactly the problem: nothing enforces it.

**Fix:** a build-time check, or move the data into the database with foreign keys, which
§D gets for free.

### B2 · Only the corpus is tested — `atlas-tst2`

15 golden tests cover parsing and mentions. There are **zero** tests for the name
morphology, the patronymic lineage, the address attribution, or the curated data. The
morphology in particular is rule-based and full of edge cases — the irregular-stem table
(`Pavl → Pavel`) is exactly the kind of thing that rots quietly.

### B3 · No CI — `atlas-ci01`

`npm run test` and `next build` are run by hand. Nothing stops a broken build being
pushed. Everything needed already exists; it just is not wired to a workflow.

### B4 · Two sources of truth for chronology — `atlas-vald`

`timeline.ts` declares segments in `SEGMENTS` and their durations in a separate
`DURATION` map in `Timeline.tsx`, keyed by string. Adding a segment in one place and
forgetting the other yields a silently mis-scaled axis.

## C. Design system v2 — remaining inconsistencies

### C1 · Shape encoding is not applied everywhere — `atlas-shp2`

`GroupMark` is wired into the relationship map, name orbits and warmth ladder. It is
**not** yet in the timeline lanes or the `/read` sidebar chips, which still use plain
circles. That breaks the rule the system just committed to: category is encoded by shape.

### C2 · Copy hardcodes numbers the corpus already knows — `atlas-shp2`

Strings like "all 96 chapters" appear in page copy instead of being derived from
`corpus.chapters.length`. If the parser ever changes, the prose lies.

### C3 · No shape legend anywhere

Shape now carries meaning and nothing explains the mapping. A legend is needed on any
page using marks.

## D. Architecture

### D1 · There is no database — `atlas-db01`

Data lives in three JSON files and 96 text files, read from disk and parsed on demand.
This has served well for the deterministic pipeline, but it blocks everything queued
next: spoiler-scoped retrieval, phrase search, reading position, and the verdict
mechanic all want query-time filtering that JSON cannot give.

### D2 · The pipeline is in the wrong language — `atlas-gc9d`

Alias resolution, morphological classification and speaker attribution are NLP, written
in TypeScript because the app was TypeScript. `pymorphy3` would replace the hand-written
suffix rules and irregular-stem table with a real analyser; spaCy could lift attribution
above its current **14%** coverage.

## F. What is genuinely good

Worth recording so it is not lost in a refactor.

- **Offsets into the source.** Every chapter records `start`/`end`, so any claim is
  traceable. This is the foundation of the project's credibility.
- **The alias bitmap.** Claiming source positions once, longest-first, is the right
  solution and is why the counts are trustworthy.
- **The verify-don't-trust habit.** Checking the alias table against the text found four
  entries that matched nothing. The builder now asserts every form occurs.
- **The computed/curated boundary**, declared in file headers rather than implied.
- **Hand-laid diagrams.** `/who` and `/timeline` are legible because their composition
  was designed, not simulated.

---

## G. Recommended order

1. `atlas-memo` — cheap, and it stops verification lying to us.
2. `atlas-vald` + `atlas-tst2` — guard the data before building on it.
3. `atlas-db01` + `atlas-gc9d` — the database and the Python service, together.
4. `atlas-shp2` + `atlas-srch` — finish the design rule; search comes free with §3.
5. Then the reader features already planned under `atlas-e56i`.
